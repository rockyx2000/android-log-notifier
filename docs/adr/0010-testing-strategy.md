# 0010. テスト戦略: 純粋なロジックを JVM で厚く、端末依存は手順書で

- 状態: 採用(層 1〜3 は実施済み、層 4 は手順書を整備)
- 日付: 2026-10-07

## 背景

v1.0 はテストなしで公開した。このアプリの失敗は、**黙って起きる** ものが多い。

- DNS の応答パケットを 1 バイト間違えると、端末の名前解決が止まる。
- 23:00 の集計範囲を 1 つ間違えると、サマリが欠ける、または二重に送られる。
- 記録対象のフィルタを間違えると、不要な履歴を保存する(→ [0002](0002-minimize-collected-data.md))。

一方で、VPN・Doze・メーカーの省電力・実際の Discord は、自動テストで再現しにくい。
すべてを自動化しようとすると、不安定なテストが増えて、信頼されなくなる。

## 決定

テストを 4 層に分け、**自動化の価値が高く、安定するところから** 作る。

| 層 | 対象 | 方法 | 状態 |
| --- | --- | --- | --- |
| 1. 単体(JVM) | `DomainFilter`、`DnsPacket`、`UdpDns`(IPv4/UDP の読み書き)、`Summary`(区切り・集計・本文・送信範囲の判断)、`Health.clip` | JUnit 4。端末不要で、数秒で終わる | **実施(53 件)** |
| 2. 計装(エミュレーター) | `AccessLog`(重複抑制・ローテーション)、`Health`(保存と途切れの記録)、`SummaryScheduler`(アラーム登録) | `androidTest`。Android の `Context` が要る部分 | **実施(40 件)** |
| 3. 結合(エミュレーター + adb) | 起動 → VPN → 名前解決 → 記録、強制終了 → 再開 → 途切れ、Wi-Fi の切断・接続 | `scripts/e2e.sh`。VPN の同意ダイアログは `appops` で事前に許可する | **実施(20 項目 + 再起動 12 項目)** |
| 4. 手動(実機) | 省電力・Doze・再起動・実際の送信・他の VPN との競合 | [手順書](../manual-test.md) | **手順書を整備** |

### 層 1 のために行った整理

`Context` に依存した関数の中にあった判断を、動作を変えずに純粋な関数として取り出した。

- `DnsVpnService` の IPv4/UDP の読み書き → `UdpDns`
- `Summary.aggregate` を、ログの行の列を受け取る形に(ファイルを読む版は、これを呼ぶだけ)
- 「初回・送信済み・送る」の判断 → `Summary.plan`(`SummaryReceiver` はこれに従う)
- 途切れの切り詰め → `Health.clip`

### 何を確かめるか(層 1)

- **境界**: 期間は「開始を含み、終了を含まない」。23:00 ちょうど、夏時間の日。
- **不正な入力**: 壊れたログの行、圧縮ポインタ、はみ出すラベル長、短すぎるパケット、不正な IHL。
- **契約**: 応答パケットのヘッダチェックサムが正しい(RFC の既知の例と照合)。送信元と宛先が入れ替わる。
- **上限**: 本文は、500 ドメインや警告つきでも Discord の 2000 文字に収まる。
- **取りこぼしの防止**: 何日分が未送信でも、前回の終端から 1 通にまとめる。

## 結果

得たもの

- テストを書く過程で、2 件の弱点が見つかり、直した。
  - `UdpDns.parse` が、IPv4 ヘッダ長(IHL)が 20 バイト未満の不正なパケットを、そのまま読もうとしていた。
  - `DomainFilter.matches` に大文字の名前を直接渡すと、一致しなかった。実際の経路では、`DnsPacket` が先に小文字にそろえるため、動作への影響はなかった。
- 以後の変更で、パケットの組み立てと集計範囲が壊れたら、数秒で気づける。

失ったもの

- JUnit を、テスト専用の依存として追加した(APK には含まれない)。[0007](0007-no-dependencies.md) の「依存を持たない」は、**配布物の依存** に限った方針として扱う。
- 層 1 は、`DnsVpnService` 本体、`SummaryReceiver`、`MainActivity` の動きを確かめない。ここは、層 2〜4 で補う。
- エミュレーターは、負荷が高いと不安定になる(テスト中に、システムが一時的に落ちた)。層 3 は、再試行や待機を組み込む前提にする。

## 検討した代替案

- **Robolectric で `Context` を模す**: 層 2 を JVM で動かせるが、依存が大きく、本物の端末との差も残る。見送った。
- **UI テスト(スクリーンショットの比較など)**: 見た目の変更が多く、保守の割に得るものが少ない。
- **すべて手動にする**: 回帰を見逃しやすい。パケットや集計のような、決まった入出力の処理には向かない。

## 追記(層 2・3 の実装)

2026-10-07 に層 2 と層 3 を実装した。判断と、分かったことを残す。

### 構成

- **層 2(`app/src/androidTest`)**: `AccessLog`(追記・重複抑制・ローテーション・集計との結合)、`Health`(途切れの記録・解除・保持期限)、`SummaryScheduler`(アラーム登録)、`SummaryReceiver`(送信範囲・成功と失敗・再試行・警告の本文)。
  - 送信の経路は、**端末内に立てた偽の Webhook サーバー**(`FakeWebhook`)で確かめる。本物の Discord には送らない。デバッグ版に限り、`127.0.0.1` への平文 HTTP を許可している。
- **層 3(`scripts/e2e.sh`)**: 開始、記録対象の判定、Wi-Fi の切断と再接続、強制終了後の自動再開と途切れの記録、停止。
  - VPN の同意ダイアログは `appops set ACTIVATE_VPN allow`、電池の除外ダイアログは `cmd deviceidle whitelist` で、事前に回避する。
- **デバッグ版は `.debug` を付けた別のアプリ**にした(`applicationIdSuffix`)。テストが保存データを消しても、リリース版の設定に影響しない。署名が違っても共存できる。
- **`android.useAndroidX=true`** にした。`androidx.test` を使うためで、アプリ本体は AndroidX に依存しない。リリース APK に `androidx` と `junit` が含まれないことを確認した。

### 分かったこと

- **テストが検出できることを確認した**: 本番コードをわざと 3 か所壊し(送信成功でも終端を進めない・重複抑制を無効・途切れの閾値を極端に大きく)、対応するテスト 8 件が落ちた。壊したコードは元に戻した。
- **不安定さの原因は、テスト側にあった**。実装の不具合ではない。
  - 記録した直後の同じミリ秒にテスト送信すると、「終了を含まない」範囲から外れる(計装テストで 1 回だけ失敗)。時刻を少し過去にして直した。
  - 存在しないドメイン(`sub.example.com`)は `unknown host` になる。ログには、存在しない名前の問い合わせも記録される。実在するドメインを使う。
  - CNAME の名前は、`ping` が正式名を表示する。名前の一致ではなく、`unknown host` の有無で見る。
  - 同じ FQDN は 60 秒以内なら 1 回とみなされるので、手順ごとに別の FQDN を使う。
- 直した後は、層 2 を 3 回、層 3 を 3 回続けて実行し、すべて成功した。

### 残る穴

- 層 3 は、エミュレーターの Wi-Fi 切断を使う。**実際の Wi-Fi とモバイル回線の切替は、実機でしか確かめられない**([手順書](../manual-test.md))。
- Doze、メーカーの省電力、再起動後の自動再開、他の VPN との競合は、エミュレーターでは再現しにくい。
- エミュレーターは、Mac の負荷が高いと、システムが一時的に落ちる。層 3 は、待機と再試行を組み込んである。

### 追記(2026-10-08): ロック画面つきの再起動

`scripts/e2e-reboot.sh` を加えた(12 項目)。PIN を設定した端末を再起動し、**ロックを解除する前に** VPN が回復すること、ロック中の記録が解除後にログへ取り込まれること、対象外のドメインはロック中も記録されないことを確かめる。[0011](0011-auto-start-and-direct-boot.md) の挙動を守る。

- `run-as` は、ロック中は CE を読めず失敗する。そのため、一時バッファの中身は、解除後の結果(ログへの取り込み)で確かめる。
- 計装テストに `StorageTest`(10 件)を加えた。更新前の状態の引き継ぎ(DE に空のファイルが先にできていても取りこぼさない)を確かめる。この観点は、テストが実際に見つけた弱点で、移行の判定方法を直した。
- 高負荷でエミュレーターの画面取得(`uiautomator`)が不安定になるため、`e2e.sh` の操作に再試行を加えた。
