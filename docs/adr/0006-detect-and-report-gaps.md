# 0006. 記録の途切れを検知してサマリで報告する

- 状態: 採用
- 日付: 2026-10-07

## 背景

[0004](0004-foreground-service-and-power.md) のとおり、常駐は OS に止められうる。
黙って止まると、「記録がない」のか「記録できていない」のかが、受け取る側に区別できない。管理の観点で、これは致命的である。

## 決定

- サービスが 60 秒ごとに、生存時刻 `last_beat` を保存する。
- サービスの開始時に、前回の生存時刻から 3 分以上空いていれば、その区間を **途切れ(gap)** として保存する(14 日分・最大 50 件)。
- ユーザー操作による停止では、`last_beat` を消す。意図した停止は、途切れとして数えない。
- 他の VPN アプリなどに奪われて OS から解除された場合は(`onRevoke`)、`revoked_at` を記録し、ユーザーが再開するまで「停止中」として報告する。
- サマリの時点で、すでに止まっている(開始状態のはずなのに、サービスが動いていない)場合も、途切れとして報告する。
- サマリには、途切れの回数と合計時間、先頭の 5 件を載せる。

## 結果

得たもの

- 「記録が空」と「記録できていなかった」を、受け取る側が区別できる。
- 途切れの原因調査(省電力の設定を見直す、など)に、時刻の手がかりが残る。

失ったもの

- 途切れの開始時刻は「最後に生存を確認できた時刻」である。スリープ中はスレッドが止まって生存時刻が更新されないので、実際に止まった時刻より早めに出ることがある(過大に報告する側に倒れる)。
- 端末の電源オフも、途切れとして報告される。
- 生存時刻の書き込みが 60 秒ごとに発生する(`SharedPreferences` の `apply`)。負荷は小さいと判断した。

## 検討した代替案

- **アラームで生存を確認する**: スリープ中でも動くが、アラームの管理が増える。今は過大報告を許容し、見送った。
- **途切れの報告を別の通知にする**: 経路が増える。サマリに載せれば、確認の手間が増えない。
